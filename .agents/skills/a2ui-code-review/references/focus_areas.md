# Review focus areas

Logic and correctness are always reviewed. On top of that, the reviewer picks
one or more focus areas from this list, or names new ones. Before the review,
suggest the areas that fit the PR (see "Suggest when") and let the reviewer
select several and add their own.

Each area below lists what to check. Brief reviewer subagents with the checks
of every selected area that applies to their scope. For a custom area, write a
short description of what to check from the reviewer's wording and confirm it
with them.

| Area                               | Suggest when the PR touches                                                                    | What to check                                                                                                                                                                                                                                                                                            |
| ---------------------------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Performance**                    | Parsers, compilers, streaming, validation, catalog or schema processing, hot loops             | Algorithmic cost (per chunk and in total; watch for O(n²) rescans), repeated work that could be cached, cache invalidation, allocations and copies of large structures, regexes with catastrophic backtracking. Back claims with timings at realistic sizes.                                             |
| **Latency and streaming**          | Response streams, renderers, transports, `<a2ui>` block handling                               | Time to first render, whether output is held back longer than needed (buffering until a block or component closes), progressive rendering, UI jitter (a component rendered with the wrong catalog or layout and then re-rendered), behavior at chunk sizes 1, 2, 7 and 1000.                             |
| **Synchronization and state**      | Data model, `RendererState`, message processors, surface lifecycle, two-way binding            | Client and agent state stay in sync; updates are atomic (a failed `feed()` or message leaves state unchanged); ordering of `createSurface`, `updateComponents`, `updateDataModel` and `deleteSurface`; stale state after delete and re-create; orphaned or superseded components; per-session isolation. |
| **Concurrency and async**          | `async` code, ADK or A2A integrations, servers, shared caches or globals                       | Blocking calls on the event loop, shared mutable state across requests or sessions (module-level maps, mutable defaults), races between streams, cancellation and cleanup (`close()` always called), thread safety of caches.                                                                            |
| **Memory and resources**           | Session state, caches, history buffers, long-lived agents                                      | Unbounded growth per session or per message, caches without limits, objects kept after a surface is deleted, file handles and worktrees not closed.                                                                                                                                                      |
| **Error handling and resilience**  | Parsers of LLM output, validation, fallbacks, retries                                          | Fail loudly instead of swallowing errors; error types and codes match across SDKs; recovery from LLM output quirks doesn't corrupt valid content; retries don't mask real failures; users never see raw DSL or invalid UI.                                                                               |
| **Cross-SDK parity**               | The same feature in more than one of Python, TypeScript, Dart, Swift                           | Same input gives the same output, error codes and paths in every SDK; fixes applied to all SDKs; conformance cases pin the behavior and every runner executes them.                                                                                                                                      |
| **Spec and protocol conformance**  | Messages, schemas, `specification/`, version adapters                                          | Behavior matches `specification/<version>` (schemas first); no version leaks or hard-coded versions; older versions keep their behavior; spec and blueprint edits are needed and minimal.                                                                                                                |
| **Catalogs and compatibility**     | Catalog loading, negotiation, pruning, mixed catalogs, `catalogId` resolution                  | Per-client catalog negotiation; pruned catalogs; components or functions missing from the client's catalog; component-level `catalogId`; surfaces without a default catalog; cross-catalog `$ref`; round-trip `fromJson`/`toJson`.                                                                       |
| **API design and compatibility**   | Public classes, constructors, exports, package facades                                         | Small public surface; no needless setters or exposed internals; required parameters are required; facade exports only; breaking changes recorded in the CHANGELOG; names say what they mean (`at_least_v10`).                                                                                            |
| **Tests and conformance coverage** | Tests, `conformance/` YAML, runners                                                            | Shared behavior in conformance YAML rather than unit tests; runners don't skip cases silently; existing cases not weakened; negative cases; tests assert the specific error.                                                                                                                             |
| **Security**                       | Renderers, HTML or Markdown output, URLs, file paths, tool or function execution, dependencies | XSS from agent or LLM content in renderers, URL and path validation, injection into prompts or expressions, untrusted function calls, new dependencies and their versions.                                                                                                                               |
| **Inference formats and prompts**  | Express, Direct JSON, prompt generators, eval                                                  | Formats stay catalog-agnostic; prompt size and token cost; prompts and parsers agree; golden prompts updated; eval changes measure what they claim.                                                                                                                                                      |
| **Accessibility and UI**           | Renderers under `typescript/renderers/`, Flutter, SwiftUI, sample clients                      | Semantic roles and labels, keyboard and focus handling, contrast, layout shifts while streaming, parity between renderers.                                                                                                                                                                               |
| **Docs and samples**               | READMEs, `docs/`, samples, CHANGELOGs                                                          | Commands in READMEs work; no stale API names; samples run and validate against the right version; CHANGELOG entries short and accurate; PR description matches the diff.                                                                                                                                 |
| **Build, CI and packaging**        | `package.json`, `pyproject.toml`, `pubspec.yaml`, workflows, release scripts                   | Canonical Yarn script targets; workspace registration; versions and dependency ranges; CI jobs cover the change; failing checks caused by the PR.                                                                                                                                                        |
| **Scope and PR size**              | Large PRs or PRs with unrelated edits                                                          | Every change serves the PR's purpose; unrelated changes split out; minimal diffs to specs, proposals and test data; whether the PR should be split.                                                                                                                                                      |

## How the focus is used

- **Scopes:** keep the default split (per SDK plus cross-SDK), and add each
  selected area to every reviewer brief it applies to. Give an area its own
  reviewer when it needs dedicated runs (for example, performance timings or
  streaming fuzzing across SDKs).
- **Narrowing:** if the reviewer narrows the scope ("only the Python changes",
  "only performance"), skip the other areas except must-fix correctness issues.
- **Coverage:** every selected area gets a one-line result in
  `focus_coverage`, including "checked, no issues found", so the reviewer can
  see that it was covered.
- **Recommendations:** findings in a selected area follow the normal severity
  defaults. Findings outside the selected areas default to `ignore` unless
  they are `must`.
